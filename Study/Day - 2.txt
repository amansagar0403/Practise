2. Primary keys and foreign keys
These concepts come first because joins rely on understanding how records relate to one another.
Primary key (PK)
A primary key uniquely identifies each row in a table.
In your schema:
CREATE TABLE users (
    id NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    full_name VARCHAR2(100) NOT NULL,
    email VARCHAR2(255) NOT NULL UNIQUE
);


Here, id is the primary key.
A primary key must satisfy these rules:
- Unique: no two rows can have the same primary key.
- Not null: every row must have a primary key value.
- One primary key constraint per table: it can contain one column or multiple columns together.
A table can have several unique constraints, but only one primary key constraint. For example, email can also be unique without being the primary key.
Why do we need it?
Imagine two customers have the same name. A name isn't a reliable way to identify a specific customer. A unique ID is.
Foreign key (FK)
A foreign key references a primary key or another eligible unique key in a different or the same table.
Your ACCOUNTS table uses:
CONSTRAINT fk_accounts_users
    FOREIGN KEY (user_id)
    REFERENCES users(id)


This enforces a rule: an account cannot reference a nonexistent user.
For example:
INSERT INTO accounts
    (user_id, account_number, balance)
VALUES
    (9999, 'ACC999999', 1000);


If user 9999 doesn't exist, Oracle rejects the insert with a foreign-key constraint violation.
PK vs FK
Feature	Primary key	Foreign key
Purpose	Identifies a row	Connects related rows
Duplicate values	Not allowed	Usually allowed
NULL values	Not allowed	Allowed unless separately prohibited
Per table	One PK constraint	Multiple FK constraints possible
Example	USERS.id	ACCOUNTS.user_id
A foreign key does not automatically create an index on its column in Oracle. Indexing can matter for join performance and for operations involving parent and child rows.
What happens when a user is deleted?
Suppose user 1 owns accounts 101 and 102. Deleting user 1 would leave those accounts pointing to a nonexistent user.
By default, the foreign key prevents deleting a parent row while referenced child rows exist. You can explicitly define other behavior, such as ON DELETE CASCADE, when appropriate, but that should be a deliberate design decision in a banking application.
Interview takeaway: Primary keys identify records; foreign keys enforce relationships and referential integrity.

3. SQL JOINs — combining data from multiple tables
A JOIN lets you retrieve related information stored in separate tables.
For example, the account table contains user_id, but not the user's name. If you want to display each account owner's name alongside the account number, you need a join.
3.1 INNER JOIN
An INNER JOIN returns only rows where the join condition matches in both tables.
SELECT
    u.id,
    u.full_name,
    a.account_number,
    a.balance
FROM users u
INNER JOIN accounts a
    ON u.id = a.user_id;


How to read it:
- FROM users u: start with USERS; u is an alias.
- INNER JOIN accounts a: combine it with ACCOUNTS.
- ON u.id = a.user_id: match each user with their accounts.
- SELECT: return the columns you want.
Expected result for our illustrative data:
id	full_name	account_number	balance
1	Test User	ACC100001	5,000
1	Test User	ACC100002	2,500
2	Rahul Sharma	ACC100003	8,000
Priya does not appear because she has no account.
Notice that Test User appears twice. This is expected: a join returns one result row per matching combination, not necessarily one row per user.

An inner join keeps only the matching portion of the two datasets.

3.2 LEFT JOIN (LEFT OUTER JOIN)
A LEFT JOIN returns every row from the left table, plus matching rows from the right table.
If there is no match, the right-side columns contain NULL.
SELECT
    u.id,
    u.full_name,
    a.account_number,
    a.balance
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id;


Result:
full_name	account_number	balance
Test User	ACC100001	5,000
Test User	ACC100002	2,500
Rahul Sharma	ACC100003	8,000
Priya Singh	NULL	NULL
Why does Priya appear now? Because USERS is the left table, and every user must be retained even when no matching account exists.
Real-world use case: Find all customers, including those who haven't opened a bank account.
SELECT u.id, u.full_name
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id
WHERE a.id IS NULL;


This returns users without accounts.
Why check a.id IS NULL? Because a.id is a non-null primary key for real account rows. When the join has no match, Oracle fills it with NULL.







campus.datacamp.com


A left join keeps the entire left dataset and adds matching information from the right.

3.3 RIGHT JOIN (RIGHT OUTER JOIN)
A RIGHT JOIN retains every row from the right table, with matches from the left table where available.
SELECT
    u.full_name,
    a.account_number,
    a.balance
FROM users u
RIGHT JOIN accounts a
    ON u.id = a.user_id;


Since ACCOUNTS.user_id has a foreign key to USERS.id, every valid account should have a matching user. Therefore, this query normally returns the same account rows as the inner join in our current schema.
You can usually rewrite a right join as a left join by swapping the table order. Many developers prefer LEFT JOIN because it makes the preserved table obvious.
3.4 FULL OUTER JOIN
A FULL OUTER JOIN returns:
- Rows where the tables match.
- Unmatched rows from the left table.
- Unmatched rows from the right table.
SELECT
    u.full_name,
    a.account_number
FROM users u
FULL OUTER JOIN accounts a
    ON u.id = a.user_id;


This can be useful for reconciling datasets or finding unmatched records on either side. With valid foreign keys in our banking schema, unmatched accounts should not normally occur.







pdq.com


A full outer join retains both sides, including unmatched records.

3.5 CROSS JOIN
A CROSS JOIN produces every possible combination of rows between two tables.
SELECT u.full_name, a.account_number
FROM users u
CROSS JOIN accounts a;


If there are 3 users and 3 accounts, the result has \(3 \times 3 = 9\) rows.
This is called a Cartesian product. It is useful when you genuinely need all combinations, but an accidental cross join can produce a huge result set.
JOIN cheat sheet
Join	What it returns
INNER JOIN	Matching rows only
LEFT JOIN	All left rows and matching right rows
RIGHT JOIN	All right rows and matching left rows
FULL OUTER JOIN	All rows from both sides
CROSS JOIN	Every possible combination
3.6 A critical JOIN mistake
Consider this query:
SELECT u.full_name, a.account_number
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id
WHERE a.balance > 1000;


You might expect it to show all users, including those without accounts. But the WHERE a.balance > 1000 condition removes rows where a.balance is NULL.
As a result, users without accounts disappear, making the result behave like an inner join for this condition.
If you want to preserve every user while only matching accounts with balances above 1000, use:
SELECT u.full_name, a.account_number, a.balance
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id
   AND a.balance > 1000;


The condition is now part of the join itself. All users remain, even if they have no qualifying account.
This distinction between ON and WHERE is an important interview topic.

4. GROUP BY — aggregating data
GROUP BY combines rows that share the same value in one or more columns, allowing you to calculate statistics for each group.
Suppose your account data is:
user_id	account_number	balance
1	ACC100001	5,000
1	ACC100002	2,500
2	ACC100003	8,000
You might want to know the total balance held by each user.
4.1 Basic GROUP BY
SELECT
    user_id,
    SUM(balance) AS total_balance
FROM accounts
GROUP BY user_id;


Result:
user_id	total_balance
1	7,500
2	8,000
What happens internally, conceptually?
1. Oracle groups account rows by user_id.
2. It calculates SUM(balance) for each group.
3. It returns one row per user ID that appears in ACCOUNTS.
It doesn't return one row per account anymore. It returns one row per group.
4.2 The five aggregate functions you should know
Function	Purpose	Example
COUNT()	Counts rows or non-null values	COUNT(*)
SUM()	Adds numeric values	SUM(balance)
AVG()	Calculates the average	AVG(balance)
MIN()	Finds the smallest value	MIN(balance)
MAX()	Finds the largest value	MAX(balance)
Examples:
SELECT
    COUNT(*) AS account_count,
    SUM(balance) AS total_balance,
    AVG(balance) AS average_balance,
    MIN(balance) AS minimum_balance,
    MAX(balance) AS maximum_balance
FROM accounts;


This query returns a single summary row for the entire table.
Important: COUNT(*) counts rows, including rows with nulls in other columns. COUNT(balance) counts only rows where balance is not null. In your schema, balance is NOT NULL, so those two counts should agree.
4.3 GROUP BY with JOIN
Now let's get each user's name, number of accounts, and total balance.
SELECT
    u.id,
    u.full_name,
    COUNT(a.id) AS account_count,
    COALESCE(SUM(a.balance), 0) AS total_balance
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id
GROUP BY u.id, u.full_name;


Why does this query use a LEFT JOIN?
Because we want users who have no accounts to appear too.
Why use COUNT(a.id) rather than COUNT(*)?
For a user without accounts, a left join still creates one result row with null account columns. COUNT(*) would count that generated row as 1, but COUNT(a.id) ignores the null account ID and returns 0.
Why use COALESCE(SUM(a.balance), 0)?
For users without accounts, SUM(a.balance) returns NULL. COALESCE replaces that null with zero.
Why group by both u.id and u.full_name?
Every selected column must either be aggregated or be included in the grouping, subject to Oracle's SQL grouping rules. Grouping by both makes the intended grouping explicit.
4.4 WHERE vs GROUP BY vs HAVING
These three clauses solve different problems.
- WHERE filters individual rows before aggregation.
- GROUP BY defines the groups.
- HAVING filters groups after aggregation.
Example: find users whose combined account balances exceed 5,000.
SELECT
    u.id,
    u.full_name,
    SUM(a.balance) AS total_balance
FROM users u
JOIN accounts a
    ON u.id = a.user_id
WHERE a.balance > 0
GROUP BY u.id, u.full_name
HAVING SUM(a.balance) > 5000;


Execution is easiest to understand in this conceptual order:
FROM / JOIN — combine tables

WHERE — filter rows

GROUP BY — form groups

HAVING — filter groups

SELECT — produce output

ORDER BY — sort results

This is a conceptual SQL processing order, not necessarily Oracle's physical execution plan.

For example, this is invalid:
SELECT user_id, SUM(balance)
FROM accounts
WHERE SUM(balance) > 5000
GROUP BY user_id;


Why? WHERE cannot filter on an aggregate result like SUM(balance). Use HAVING instead.
4.5 GROUP BY mistakes
Mistake 1: Selecting a column that isn't grouped or aggregated
SELECT user_id, account_number, SUM(balance)
FROM accounts
GROUP BY user_id;


This is invalid in Oracle because account_number is neither aggregated nor grouped.
Mistake 2: Counting the wrong thing
COUNT(*)


counts result rows, whereas:
COUNT(a.id)


counts matched accounts when a.id is a non-null account primary key.
Mistake 3: Using WHERE instead of HAVING
Use WHERE balance > 0 to filter individual accounts. Use HAVING SUM(balance) > 5000 to filter groups by their combined balance.

5. Put the concepts together: banking SQL queries
These are practical queries worth knowing for your current project and SDE interviews.
Query 1 — List accounts with their owners
SELECT
    a.id AS account_id,
    a.account_number,
    a.balance,
    u.full_name,
    u.email
FROM accounts a
JOIN users u
    ON a.user_id = u.id
ORDER BY a.id;


Tests: INNER JOIN, aliases, sorting.
Query 2 — Find users with no accounts
SELECT u.id, u.full_name
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id
WHERE a.id IS NULL;


Tests: LEFT JOIN, NULL, unmatched rows.
Query 3 — Count accounts per user
SELECT
    u.full_name,
    COUNT(a.id) AS account_count
FROM users u
LEFT JOIN accounts a
    ON u.id = a.user_id
GROUP BY u.id, u.full_name
ORDER BY account_count DESC;


Tests: LEFT JOIN, COUNT, GROUP BY, ORDER BY.
Query 4 — Find users with more than one account
SELECT
    u.id,
    u.full_name,
    COUNT(a.id) AS account_count
FROM users u
JOIN accounts a
    ON u.id = a.user_id
GROUP BY u.id, u.full_name
HAVING COUNT(a.id) > 1;


Tests: aggregation and HAVING.
Query 5 — Find accounts with balances above the average
SELECT account_number, balance
FROM accounts
WHERE balance > (
    SELECT AVG(balance)
    FROM accounts
);


This introduces a subquery: a query nested inside another query. The inner query calculates the average balance; the outer query selects accounts exceeding it.

What you should remember for interviews
- Primary key: uniquely identifies a record.
- Foreign key: ensures a reference points to a valid parent record.
- INNER JOIN: only matching rows.
- LEFT JOIN: all left-side rows, with NULL for missing matches.
- GROUP BY: aggregates rows into groups.
- WHERE: filters rows before grouping.
- HAVING: filters groups after aggregation.
- COUNT(*) vs COUNT(column): the former counts rows; the latter ignores null values.
- Subquery: a query nested within another query.
